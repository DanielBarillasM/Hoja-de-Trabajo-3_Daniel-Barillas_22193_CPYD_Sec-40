\begin{summarybox}
Esta hoja de trabajo desarrolla tres competencias fundamentales de CUDA. La
primera parte implementa una suma de arreglos en GPU y analiza la separación
entre host y device. La segunda completa la plantilla \code{vacio.cu} para
clasificar valores respecto de un umbral. La tercera construye una versión
secuencial en CPU y un comparador reproducible CPU/GPU que distingue el tiempo
del kernel del costo completo de transferencias. Las salidas disponibles
validan numéricamente las Partes 1 y 2 y la línea base CPU. El comparador queda
listo para ejecutarse en el equipo CUDA de entrega, sin sustituir mediciones
reales por estimaciones.
\end{summarybox}

\section{Fundamentos del modelo CUDA}

Un programa CUDA combina dos espacios de ejecución. El \textit{host}, que
corresponde a la CPU, coordina el programa y administra recursos. El
\textit{device}, que corresponde a la GPU, ejecuta kernels sobre una gran
cantidad de hilos. En esta actividad se usa memoria separada: un puntero host
no sustituye a un puntero device y los datos deben transferirse de forma
explícita.

El índice global unidimensional se calcula mediante:

\[
  i = \texttt{blockIdx.x}\cdot\texttt{blockDim.x}
      + \texttt{threadIdx.x}
\]

Cada hilo procesa un índice independiente. Como el número de hilos lanzados
puede superar el número de datos, todos los kernels incluyen la condición
\(\texttt{i < N}\).

\subsection{Flujo general}

\begin{enumerate}
  \item Crear e inicializar datos en el host.
  \item Reservar memoria device con \code{cudaMalloc}.
  \item Copiar entradas mediante \code{cudaMemcpyHostToDevice}.
  \item Calcular grid y block.
  \item Lanzar el kernel.
  \item comprobar el lanzamiento y sincronizar.
  \item Copiar resultados mediante \code{cudaMemcpyDeviceToHost}.
  \item Validar y liberar recursos.
\end{enumerate}

\section{Parte 1: suma de arreglos en GPU}

\subsection{Objetivo y datos}

La primera parte suma dos arreglos de \(N=16\) elementos. La inicialización es:

\[
  A[i] = i+1,\qquad B[i]=2i+3
\]

Por lo tanto, el valor esperado es:

\[
  C[i]=A[i]+B[i]=3i+4
\]

\subsection{Kernel}

\begin{Verbatim}[frame=single,framesep=3mm,fontsize=\small,
  rulecolor=\color{ElectricBlue},formatcom=\color{DarkGray}]
__global__ void sumarArreglos(
    const int *A, const int *B, int *C, int N) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < N) {
        C[idx] = A[idx] + B[idx];
    }
}
\end{Verbatim}

El programa usa bloques de ocho hilos y dos bloques. La condición de límites
mantiene el kernel correcto incluso si se cambia a una configuración que lance
más hilos que elementos.

\subsection{Resultado observado}

\begin{figure}[H]
  \centering
  \includegraphics[width=0.78\textwidth,height=0.72\textheight,keepaspectratio]{parte-1.png}
  \caption{Compilación y ejecución de la suma de arreglos en CUDA.}
  \label{fig:parte1}
\end{figure}

La Figura~\ref{fig:parte1} muestra \(C[0]=4\), \(C[1]=7\) y una progresión de
tres unidades hasta \(C[15]=49\). Estos valores coinciden exactamente con
\(3i+4\). La captura también evidencia la configuración \code{grid = 2} y
\code{block = 8}, además del regreso de la salida al host.

\subsection{Respuestas requeridas}
\label{sec:preguntas}

\subsubsection{¿Qué partes se ejecutan en CPU y cuáles en GPU?}

La CPU ejecuta \code{main}, inicializa A y B, invoca \code{cudaMalloc}, ordena
las copias, calcula la configuración de lanzamiento, verifica errores, imprime
la salida y libera memoria. La GPU ejecuta únicamente el cuerpo del kernel:
cada hilo calcula un índice y suma dos enteros.

\subsubsection{¿Qué ocurre al cambiar grid y block?}

El total de hilos es \(\textit{gridSize}\times\textit{blockSize}\). Si es menor
que \(N\), algunos elementos nunca se procesan. Si es mayor, la comprobación
\code{idx < N} descarta los hilos sobrantes. El tamaño de bloque también afecta
el rendimiento: bloques demasiado pequeños pueden desaprovechar recursos,
mientras bloques muy grandes pueden reducir ocupación o exceder límites del
dispositivo. Por ello se usa la división de techo:

\[
  \textit{gridSize} =
  \left\lceil \frac{N}{\textit{blockSize}} \right\rceil
\]

\subsubsection{¿Qué ocurre si no se reserva o libera memoria?}

Sin \code{cudaMalloc}, las direcciones device no son válidas y las copias o el
kernel devuelven errores. Liberar memoria antes de terminar causa accesos
inválidos. No liberarla al final produce una fuga que puede agotar la memoria
de la GPU en ejecuciones repetidas.

\subsubsection{¿Qué ocurre si no se transfiere el resultado a CPU?}

El arreglo calculado permanece en \code{d_C}. \code{h_C} no se actualiza de
forma automática porque host y device usan espacios de memoria distintos. Sin
\code{cudaMemcpyDeviceToHost}, la CPU no dispone de los valores para
imprimirlos o utilizarlos en otra operación.

También se mantiene \code{parte2_umbral_clasificacion.cu}, una variante con

cerca al archivo original.

\subsection{Regla de clasificación}

Para \(N=32\), el arreglo contiene \(0,5,10,\ldots,155\). La salida se define:

\[
 salida[i] =
 \begin{cases}
  1, & entrada[i] \ge 50\\
  0, & entrada[i] < 50
 \end{cases}
\]

\begin{Verbatim}[frame=single,framesep=3mm,fontsize=\small,
  rulecolor=\color{ElectricBlue},formatcom=\color{DarkGray}]
__global__ void clasificarUmbral(
    const int *entrada, int *salida, int N, int umbral) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < N) {
        salida[idx] = (entrada[idx] >= umbral) ? 1 : 0;
    }
}
\end{Verbatim}

\section{Parte 3: versión CPU y comparación de tiempos}

\subsection{Versión exclusivamente CPU}

El archivo \code{parte3_cpu_vs_gpu.cpp} implementa la misma suma mediante un
ciclo secuencial. El vector de salida se calcula así:

\begin{Verbatim}[frame=single,framesep=3mm,fontsize=\small,
  rulecolor=\color{ElectricBlue},formatcom=\color{DarkGray}]
void sumarArreglosCPU(
    const std::vector<int>& A,
    const std::vector<int>& B,
    std::vector<int>& C) {
    for (std::size_t i = 0; i < A.size(); ++i) {
        C[i] = A[i] + B[i];
    }
}
\end{Verbatim}

\begin{figure}[H]
  \centering
  \includegraphics[width=0.96\textwidth,height=0.48\textheight,keepaspectratio]{parte-3.png}
  \caption{Evidencia histórica de la versión CPU: 2\,787 microsegundos para un millón de elementos.}
  \label{fig:cpu}
\end{figure}

La Figura~\ref{fig:cpu} valida la versión secuencial y sus primeros valores
\(4,7,10,13,16\). Ese tiempo es una línea base histórica y no se compara con
la nueva versión GPU porque el tamaño del problema y la ejecución no son los
mismos.

\subsection{Diseño de la comparación justa}

El nuevo archivo \code{parte3_comparacion_cpu_gpu.cu} ejecuta CPU y GPU sobre
los mismos 8\,388\,608 elementos. Reserva los vectores de salida antes de
medir, realiza un calentamiento CUDA y comprueba todos los resultados.

Se informan dos tiempos GPU:

\begin{enumerate}
  \item \textbf{Solo kernel}: medido mediante \code{cudaEventRecord}; representa
  el cálculo en el dispositivo.
  \item \textbf{Extremo a extremo}: incluye las copias H2D, el kernel y la copia
  D2H; excluye \code{cudaMalloc} y \code{cudaFree}.
\end{enumerate}

Esta separación evita una conclusión engañosa. Una GPU puede ejecutar el
kernel rápidamente y, aun así, perder ventaja si el problema es pequeño o las
transferencias dominan el costo total.

\section{Reproducibilidad y limitaciones}

\subsection{Reproducibilidad}

El script \code{scripts/compilar.sh} compila y ejecuta todos los programas.
Cada salida se conserva como texto en \code{results/}. Los ejecutables se
guardan en \code{build/}, directorio excluido de la entrega para respetar la
instrucción de no entregar binarios.

\subsection{Factores que afectan el tiempo}

Los tiempos dependen del procesador, modelo de GPU, versión del controlador,
frecuencias, temperatura, procesos concurrentes y optimizaciones del
compilador. Por ello:

\begin{itemize}
  \item no se comparan capturas obtenidas con tamaños diferentes;
  \item no se trasladan tiempos desde otro equipo;
  \item se documenta qué operaciones incluye cada medición;
  \item se valida corrección antes de interpretar velocidad.
\end{itemize}

\subsection{Fecha del documento}

El enunciado indica simultáneamente “Semestre 2, 2025” y “miércoles 21 de
octubre”. El informe conserva el semestre declarado y evita generar una fecha
automática con \code{\textbackslash today}, que podría introducir un año ajeno
a la actividad.

\section{Conclusiones}

La suma vectorial demuestra un caso de paralelismo de datos directo: cada hilo
trabaja sobre un elemento y no necesita comunicarse con otros hilos. Los
resultados \(4,7,10,\ldots,49\) confirman que la indexación, las transferencias
y el kernel son correctos.

La clasificación por umbral consolida el mismo patrón con una decisión
independiente por dato. La transición exacta en 50 valida la condición
\code{entrada[idx] >= umbral} y demuestra que la plantilla original fue
completada de acuerdo con el enunciado.

La Parte 3 distingue correctamente entre demostrar paralelismo y demostrar
rendimiento. No basta afirmar que una GPU es más rápida: deben usarse los
mismos datos, establecer los límites temporales y comprobar la salida. El
comparador implementado mide por separado el kernel y el ciclo completo,
permitiendo analizar tanto capacidad de cálculo como costo de comunicación.

En conjunto, la actividad evidencia el ciclo completo de una aplicación CUDA:
preparación en CPU, administración explícita de memoria, distribución en
hilos, sincronización, retorno de datos y validación. La única evidencia
pendiente es la medición específica de hardware, que debe obtenerse en el
equipo CUDA y colocarse en la Tabla~\ref{tab:tiempos}.
